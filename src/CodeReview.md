## Что ревьюилось

Рефакторинг `DatabaseItemPage`: логика действий вынесена в хуки и API-модули, добавлена публикация

## Итог

Блокирующих багов нет, ESLint чистый, продакшен-сборка проходит, импорты и алиасы корректны,

Все четыре заметные проблемы исправлены, ниже — только то, что осталось открытым.

## Хвосты от исправленных проблем

- **Кнопки действий не рендерятся в ветке ошибки.** Страница показывает только строку
  «Error while loading item details». Уведомление там уже живёт, а кнопки нет. Выносить ли их
  наружу — вопрос дизайна: удаление битой записи может быть полезным, но кнопка поверх сообщения
  об ошибке выглядит спорно.
- **`isPending` остаётся истинным у отключённого запроса** (`enabled: false`) и при
  `fetchStatus: 'paused'` без сети — в обоих случаях будет вечный «Loading...». Сейчас `enabled`
  в `useItemDetailsPrivate` на этом маршруте всегда истинен, но если появится валидация id
  с отключением запроса, понадобится `isLoading` (`isPending && isFetching`) либо ранний выход
  по невалидному id, как в `UploadPage` через `isValidPostId`.
- **Взаимная блокировка действий работает только на уровне UI.** `run` внутри `useConfirmedAction`
  по-прежнему знает про свой собственный `isBusy`, а про соседние действия — нет. Для кликов это
  надёжно (disabled-кнопка не порождает событий, а React успевает применить флаг между двумя
  кликами), но если `actions[i].onClick` когда-нибудь начнут дёргать программно, гард придётся
  поднимать внутрь хука — например, сделав общее состояние занятости управляемым извне.
- **Уведомление об успешном удалении показать нельзя:** локальное состояние умирает вместе со
  страницей. Если понадобится, подтверждение придётся передавать на страницу базы через
  `navigate(..., { state })`.
- **Двойное центрирование текста в окне уведомления** (`position: relative` + `top/left: 50%` +
  `translate(-50%, -50%)` у `span` внутри и без того отцентрованного окна) перенесено в общий
  компонент байт-в-байт. Разбор показывает, что это, скорее всего, no-op: `span` — флекс-элемент
  `.inner-window`, по ширине `stretch` гасит сдвиг точно, а по высоте все контейнеры растут
  по контенту. Удалять стоит отдельным изменением с проверкой обоих окон глазами.
- **Доступность, возможные доработки.** Для ошибок семантически точнее `role="alert"` (ассертивный
  регион, прерывает чтение), но менять роль на лету у одного узла ненадёжно — понадобятся два
  региона, polite и assertive. Отдельный вопрос — время жизни уведомления: 2 секунды не проходят
  по WCAG 2.2.1 (Timing Adjustable), уведомление стоило бы закрывать по клику, а не по таймеру.

## Мелочи и консистентность

- **Нет валидации id.** `UploadPage` использует `isValidPostId`, на странице базы проверка только
  `!itemId`, поэтому для URL вида `/database/item/abc` кнопка Delete активна и уходит запросом
  на сервер. Заменить `disabled: !itemId` на `disabled: !isValidPostId(itemId)`. Важно, что
  кодирование id в билдерах путей `Constants.js` эту дыру не закрывает: `encodeURIComponent`
  не трогает точку, поэтому id `..` проходит сквозь `segment()` без изменений, а URL-нормализация
  схлопывает сегмент — `post/delete/..` становится `post/`. Кодирование отвечает за то, чтобы id
  не развалил путь, а за то, чтобы id вообще был похож на id, отвечает валидация.
- **`Content-Type: application/json` на POST без тела** в `sendItem`. Часть бэкендов на пустом теле
  с таким заголовком отвечает 400 на попытке разбора JSON. Либо убрать заголовок, либо слать
  `body: "{}"` — сверить с API.
- **Успех определяется только HTTP-статусом.** API возвращает конверт `{status, message, data}`
  (см. док-комментарий в `fetchWhatsappLink.js`); если публикация ответит 200 с `status: "error"`,
  пользователь увидит «posted to Instagram». Если конверт содержательный — проверять его в `sendItem`.
- **Ручного обновления данных в приложении нет.** Внутри окна свежести молчат `refetchOnMount`,
  `refetchOnWindowFocus` и `refetchOnReconnect`, поэтому единственный способ получить свежие
  данные — перезагрузка страницы. Компонента pull-to-refresh при этом не существует:
  в `Components/Window/` лежат только `AdminLabel`, `ButtonLayer`, `InnerWindow`, `OuterWindow`,
  `ScrollContainerContext` и `WindowHeader`. Написан один стиль `Styles/Window/PullToRefresh.scss`,
  и его никто не импортирует — в бандл он не попадает. Чтобы закрыть пункт, компонент надо сначала
  написать и уже потом монтировать в `Layout`. Заодно в стиле: `left: 50%` без
  `transform: translateX(-50%)`, то есть плашка встанет правее центра.
- **Просроченная сессия заметится позже.** Обработчики `401` живут в `queryFn`
  (`useItemDetailsPrivate`, `usePrivateCatalogItems`), а с ненулевым `staleTime` маунт страницы
  отдаёт кэш без запроса. Пользователь увидит приватные данные и узнает о разлогине только на
  действии, рефетче по фокусу или pull-to-refresh. Если это мешает, лечится периодической
  перепроверкой в `AuthContext`, а не возвратом `staleTime: 0`.
- **Нет ни одного теста.** Весь рефакторинг проверен только сборкой и грепом. Дешёвая страховка —
  юнит-тесты на билдеры путей из `Constants.js`: двойное кодирование id неотличимо от корректной
  работы на числовых id и проявляется только на значениях со спецсимволами.

# Ревью изменений: кеш запросов и свежесть данных

Дата ревью: 16.08.2026

## Что ревьюилось

Незакоммиченные изменения: пороги `staleTimes` в `Constants.js` и дефолтный `staleTime`
в `index.js`, новый модуль `Components/utils/itemCache.js`, перевод каталога на
`placeholderData: keepPreviousData`, `refetchOnMount: "always"` в гидрации формы загрузки,
проброс опций в `useItemDetailsPrivate`.

## Итог

ESLint чистый, продакшен-сборка проходит. Исправлено по ходу ревью: ключ запроса каталога
переведён с объекта фильтров на строку запроса (`useCatalogItems.js`). До этого каждый заход
в каталог давал два одинаковых запроса — `filtersState` равен `{}` до инициализации
`useUrlFilters` и объекту с пустыми значениями по умолчанию после, ключи разные, а строка
запроса у обоих пустая. С `keepPreviousData` второй запрос стал ещё и виден: грид на секунду
гас до 45% непрозрачности при каждом открытии каталога.

Закрыт пункт «Публикация в соцсети не трогает кеш»: бэкенд факт публикации в вещь не отдаёт,
в деталях и списках такого поля нет, инвалидировать после `sendItemToInstagram`/`sendItemToTelegram`
нечего. Вместо вызовов `invalidateItem`/`invalidateItemLists` дописаны комментарии в `itemCache.js`
и `useItemActions.js`: появится поле со статусом публикации — инвалидацию придётся добавить,
иначе внутри `staleTimes.details` вещь будет выглядеть неопубликованной и админ опубликует её
второй раз.

Закрыт пункт «Две инвалидации подряд на обновлении»: `onSuccess` в `handleUpdateSubmit` переведён
на `Promise.all`. Заявленного в пункте эффекта при этом не было — кнопка Update держалась занятой
один круг, а не два. `invalidateQueries` рефетчит только активные запросы, а списки каталога
и базы со страницы редактирования неактивны: их инвалидация сводится к синхронной пометке
«протухло» и резолвится в том же тике. Сети касается только `invalidateItem`, и ожидание этого
рефетча оставлено намеренно — пока данные догружаются, кнопка заблокирована. Правка нужна была
не ради скорости, а чтобы код не изображал зависимость между независимыми вызовами.

Закрыт пункт «`opacity` заводит stacking context»: поведение верное, не хватало объяснения рядом
с правилом. В `FiltersItemsWrapper.scss` дописано, почему коробка у `.catalog-items-pane--pending`
безопасна (блок непозиционирован → уровень `z-index: 0`, ниже backdrop и оверлея снаружи; внутри
грида нет ни одного `z-index`) и чем это отличается от `.filters-items-wrapper`. Там же —
две ловушки на будущее: `z-index` внутри грида сломается только на время смены фильтра,
а замена `opacity` на `filter`/`will-change` добавит containing block для `position: fixed`.

Закрыты пункты «Ветка ошибки каталога забирает с собой кнопки фильтров» и «Ветка `isLoading`
в каталоге недостижима» — одной правкой в `CatalogPage.js`. Ошибка переехала внутрь
`.filters-items-wrapper` на место грида, кнопки Filters и Reset остаются на экране, так что
сломавший запрос фильтр можно сбросить без перезагрузки. Недостижимая ветка `isLoading` из JSX
убрана: после раннего выхода по `!initialized` отсутствие данных означает ошибку.

По ходу правки нашлась ещё одна дыра, которой в отчёте не было: ранний выход по `!initialized`
стоит выше выхода по `error`, а `initialized` включается только из `data.filters`, поэтому
упавший первый запрос оставлял страницу с вечным «Loading...», а ветка ошибки не срабатывала
вовсе. Теперь этот выход сам выбирает текст по `error`. Заодно зафиксировано, почему при ошибке
нельзя оставить старый список: `placeholderData` в query-core применяется только при
`status === "pending"` (`queryObserver.js:265`) и на ошибке отбрасывается вместе с данными.

Исправлена регрессия самого ревьюируемого изменения: при переносе строки запроса в ключ кеша
`useCatalogItems` стал звать `fetchItems` с полем `queryString`, а модуль принимает `query`
(`fetchItems.js:10`). Лишнее поле молча игнорировалось, `query` уходил в дефолт `""`, и на сервер
летел `post/all` без строки запроса — фильтры не доезжали вообще, при том что ключ кеша менялся,
запрос уходил и грид перерисовывался. Внешне выглядело как «фильтр ничего не отсёк».
Возвращено `query: queryString`; переименовывать параметр в `fetchItems` нельзя — его же зовёт
`usePrivateCatalogItems.js:13`.

Закрыт пункт «Порядок хуков в `DatabaseItemPage` стал значимым» — правкой комментария, без
изменения кода. Разбор показал, что вывод пункта перевёрнут: порядков всего два, и текущий
(`useItemActions` выше `useItemDetailsPrivate`) как раз тот, где `removeItem` бежит до отписки;
перестановка сделала бы старый комментарий правдой, а не вернула бы баг. Но и она ничего
не решает: для бага мало живого подписчика, нужен рендер между `removeQueries` и отпиской —
он пересоздаёт запись через `queryObserver.#updateQuery` → `queryCache.build` и уходит
за удалённым id. Внутри одного размонтирования рендера не бывает, поэтому код корректен
при любом порядке. В комментарии теперь названа эта гарантия и единственный реальный способ
её нарушить — перенести вызов обратно в `onSuccess`. Вариант с `setTimeout` в cleanup
рассматривался и отклонён: неотменяемый таймер и налог на будущие тесты ради двух
гипотетических сценариев, причём главный (перенос в `onSuccess`) он всё равно не закрывает.

Закрыт пункт «`useItemDetailsPrivate` принимает больше опций, чем обещает»: вместо `...options`
хук принимает именованный параметр — `(itemID, { refetchOnMount } = {})`. Ключ, `queryFn`
и `enabled` переопределить больше нечем, их просто некуда передать, и защищать их порядком
ключей в объекте не требуется. Заодно контракт сузился: `staleTime` снаружи тоже больше
не переопределить, он жёстко берётся из `staleTimes.details` — ни один вызов этим не пользовался,
а политика свежести по договорённости живёт в `Constants.js`. `refetchOnMount` прокидывается
безусловно, и `undefined` там безопасен: в `queryObserver.js` значение не `"always"` и не `false`,
поэтому решение отдаётся `isStale`, а затирать нечего — глобальные дефолты в `index.js` задают
только `staleTime`, `setQueryDefaults` в проекте не зовут.

Закрыт пункт «`aria-busy` висит не на том узле»: атрибут переехал с `.filters-items-wrapper`
на тот же `div`, что получает `catalog-items-pane--pending` (`CatalogPage.js:72-75`). Окно
фильтров больше не попадает в занятое поддерево — а именно в нём пользователь и находится
в момент смены фильтра. Визуальный и семантический признаки устаревания теперь на одном узле
и не рассинхронизируются. В ветке ошибки атрибута нет вовсе, и это верно: там ничего не грузится.
Живого региона на каталоге по-прежнему нет — `aria-busy` умеет сказать «подожди», но не «готово,
12 вещей»; это оставлено за рамками правки намеренно.

Заодно счётчик изображений в `ItemImageGallery.js:188` переведён с `aria-live="polite"`
на `role="status"`: роль даёт тот же polite плюс неявный `aria-atomic="true"`, то есть регион
зачитывается целиком, а не одним изменившимся куском. Регион появляется вместе с галереей
(при пустом `images` компонент возвращает `null`, `ItemImageGallery.js:50`), но первое изменение
счётчика происходит по действию пользователя, много позже монтирования, — на регистрацию региона
времени хватает. От CSS счётчик не скрыт.

Закрыты оба пункта, которые сами же и возникли из правок выше. Второй аргумент
`useItemDetailsPrivate` разбирается теперь через `const { refetchOnMount } = options ?? {}`,
а не дефолтом параметра: дефолт срабатывает только на `undefined`, поэтому `null` падал
с `TypeError` там, где прежний спред `...null` был безобидным no-op. Счётчик галереи получил
`aria-live="polite"` рядом с `role="status"` — как в `StatusNotificationWindow.js:25`, чтобы
живой регион в репозитории писался одним способом; роль и без того подразумевает polite,
явный атрибут здесь страховка от старых связок браузер+скринридер, а не смена поведения.

Ниже — то, что осталось открытым.

## Баги

- **Без сети каталог залипает полупрозрачным и некликабельным.** При дефолтном
  `networkMode: "online"` запрос, начатый без сети, ставится на паузу, а не падает: `status`
  остаётся `pending`, `error` не появляется, ветка ошибки в `CatalogPage` не срабатывает.
  `isPlaceholderData` при этом остаётся истинным сколь угодно долго, а `.catalog-items-pane--pending`
  держит `opacity: .45` и `pointer-events: none`. Пользователь с телефона переключает фильтр
  в метро и получает тусклый каталог с мёртвыми ссылками и без единого сообщения. Как минимум
  не гасить `pointer-events`, как максимум — показывать отдельное состояние по `isPaused`.
  Сюда же залипает `aria-busy`: после переезда он живёт на той же панели (`CatalogPage.js:74`)
  и в паузе бессрочно остаётся `true` — скринридеру предлагают дождаться обновления, которого
  не будет.
