# Ревью изменений: действия над вещью на странице базы

Дата ревью: 12.08.2026

В файле остаются только открытые вопросы. Разбор закрытых проблем и причины принятых
решений — в истории правок этого файла.

## Что ревьюилось

Рефакторинг `DatabaseItemPage`: логика действий вынесена в хуки и API-модули, добавлена публикация
вещи в Instagram и Telegram с окном уведомления. По ходу правок по этому отчёту окно уведомления
заменено общим `Components/StatusNotificationWindow.js` + `Styles/StatusNotificationWindow.scss`,
на который переведена и страница загрузки.

## Итог

Блокирующих багов нет, ESLint чистый, продакшен-сборка проходит, импорты и алиасы корректны,
API-модули следуют конвенциям репозитория (`credentials: "include"`, ошибка с полем `.status`).
Все четыре заметные проблемы исправлены, ниже — только то, что осталось открытым.

## Хвосты от исправленных проблем

- **Взаимная блокировка действий работает только на уровне UI.** `run` внутри `useConfirmedAction`
  по-прежнему знает про свой собственный `isBusy`, а про соседние действия — нет. Для кликов это
  надёжно (disabled-кнопка не порождает событий, а React успевает применить флаг между двумя
  кликами), но если `actions[i].onClick` когда-нибудь начнут дёргать программно, гард придётся
  поднимать внутрь хука — например, сделав общее состояние занятости управляемым извне.
- **Уведомление об успешном удалении показать нельзя:** локальное состояние умирает вместе со
  страницей. Если понадобится, подтверждение придётся передавать на страницу базы через
  `navigate(..., { state })`.
- **Двойное центрирование текста в окне уведомления** (`position: relative` + `top/left: 50%` +
  `translate(-50%, -50%)` у `span` внутри и без того отцентрованного окна) перенесено в общий
  компонент байт-в-байт. Разбор показывает, что это, скорее всего, no-op: `span` — флекс-элемент
  `.inner-window`, по ширине `stretch` гасит сдвиг точно, а по высоте все контейнеры растут
  по контенту. Удалять стоит отдельным изменением с проверкой обоих окон глазами.
- **Доступность, возможные доработки.** Для ошибок семантически точнее `role="alert"` (ассертивный
  регион, прерывает чтение), но менять роль на лету у одного узла ненадёжно — понадобятся два
  региона, polite и assertive. Отдельный вопрос — время жизни уведомления: 2 секунды не проходят
  по WCAG 2.2.1 (Timing Adjustable), уведомление стоило бы закрывать по клику, а не по таймеру.

## Мелочи и консистентность

- **`Content-Type: application/json` на POST без тела** в `sendItem`. Часть бэкендов на пустом теле
  с таким заголовком отвечает 400 на попытке разбора JSON. Либо убрать заголовок, либо слать
  `body: "{}"` — сверить с API.
- **Успех определяется только HTTP-статусом.** API возвращает конверт `{status, message, data}`
  (см. док-комментарий в `fetchWhatsappLink.js`); если публикация ответит 200 с `status: "error"`,
  пользователь увидит «posted to Instagram». Если конверт содержательный — проверять его в `sendItem`.
- **Ручного обновления данных в приложении нет.** Внутри окна свежести молчат `refetchOnMount`,
  `refetchOnWindowFocus` и `refetchOnReconnect`, поэтому единственный способ получить свежие
  данные — перезагрузка страницы. Компонента pull-to-refresh при этом не существует:
  в `Components/Window/` лежат только `AdminLabel`, `ButtonLayer`, `InnerWindow`, `OuterWindow`,
  `ScrollContainerContext` и `WindowHeader`. Написан один стиль `Styles/Window/PullToRefresh.scss`,
  и его никто не импортирует — в бандл он не попадает. Чтобы закрыть пункт, компонент надо сначала
  написать и уже потом монтировать в `Layout`. Заодно в стиле: `left: 50%` без
  `transform: translateX(-50%)`, то есть плашка встанет правее центра.
- **Просроченная сессия заметится позже.** Обработчики `401` живут в `queryFn`
  (`useItemDetailsPrivate`, `usePrivateCatalogItems`), а с ненулевым `staleTime` маунт страницы
  отдаёт кэш без запроса. Пользователь увидит приватные данные и узнает о разлогине только на
  действии, рефетче по фокусу или pull-to-refresh. Если это мешает, лечится периодической
  перепроверкой в `AuthContext`, а не возвратом `staleTime: 0`.
- **Нет ни одного теста.** Весь рефакторинг проверен только сборкой и грепом. Дешёвая страховка —
  юнит-тесты на билдеры путей из `Constants.js`: двойное кодирование id неотличимо от корректной
  работы на числовых id и проявляется только на значениях со спецсимволами.

# Ревью изменений: кеш запросов и свежесть данных

Дата ревью: 16.08.2026

## Что ревьюилось

Незакоммиченные изменения: пороги `staleTimes` в `Constants.js` и дефолтный `staleTime`
в `index.js`, новый модуль `Components/utils/itemCache.js`, перевод каталога на
`placeholderData: keepPreviousData`, `refetchOnMount: "always"` в гидрации формы загрузки,
проброс опций в `useItemDetailsPrivate`.

## Итог

ESLint чистый, продакшен-сборка проходит. Разобранные по ходу ревью пункты закрыты — разбор
и причины принятых решений в истории правок этого файла. Ниже — то, что осталось открытым.

## Баги

- **Без сети каталог залипает полупрозрачным и некликабельным.** При дефолтном
  `networkMode: "online"` запрос, начатый без сети, ставится на паузу, а не падает: `status`
  остаётся `pending`, `error` не появляется, ветка ошибки в `CatalogPage` не срабатывает.
  `isPlaceholderData` при этом остаётся истинным сколь угодно долго, а `.list-items-pane--pending`
  держит `opacity: .45` и `pointer-events: none`. Пользователь с телефона переключает фильтр
  в метро и получает тусклый каталог с мёртвыми ссылками и без единого сообщения. Как минимум
  не гасить `pointer-events`, как максимум — показывать отдельное состояние по `isPaused`.
  Сюда же залипает `aria-busy`: после переезда он живёт на той же панели
  и в паузе бессрочно остаётся `true` — скринридеру предлагают дождаться обновления, которого
  не будет. Тот же баг теперь у страницы базы: и грид, и класс общие
  (`Styles/Filters/FiltersItemsWrapper.scss`, `keepPreviousData` в `usePrivateCatalogItems`).
- **Бэкенд отдаёт «вещи нет» кодом 200.** Проверено живыми запросами 25.10.2026:
  `GET post/detail/999999` отвечает `200` с телом `{"status": false, "message": "Post not
  found"}` и без ключа `data`; успех — то же `200`, но `{"status": true, ..., "data": {...}}`.
  Остальные отказы коды несут правильные: `post/detail/abc` → `422`, `user/me` без сессии →
  `401`. То есть дыра одна — промах по id, и закрыть её нужно одним `404`, а не переписывать
  весь контракт. Пока она есть, кеши (браузер, CDN, TanStack Query) считают промах валидным
  ответом и кладут его к себе, мониторинг видит 100% успешных запросов, а каждый клиент
  обязан помнить про конвенцию конверта. Во фронте промах уже нормализуется
  в `fetchItemDetails.js` в ошибку с `.status = 404`, поэтому переход не требует
  согласованного релиза: когда сервер начнёт отдавать настоящий `404`, сработает ветка
  `!resp.ok` и бросит ровно то же самое.
  Что изменится в поведении после правки бэкенда (проверено по коду):
  - `deleteItem.js` и `sendItemToSocial.js` смотрят только на `resp.ok`, поэтому сейчас
    провалившееся удаление считается успехом (вещь исчезает из кеша и UI уходит в список,
    хотя на сервере она осталась), а провалившаяся публикация показывает «posted to
    Instagram». После правки обе начнут честно сообщать об ошибке — это починка, но внешне
    выглядит как «появились ошибки там, где их не было».
  - `submitForm` в `UploadPageForm` ветвится по `response.ok`, поэтому отказы валидации
    с бэкенда сейчас показывают успех; после правки форма начнёт их показывать.
  - `AuthContext` уже обрабатывает `!response.ok` и ставит `hasChecked` в `finally`,
    так что переход `user/me` на `401` безопасен.
  - Главный риск неаккуратной миграции: пустой список обязан остаться `200` с `data: []`.
    Если `post/all` начнёт отдавать `404` на отсутствие результатов, `fetchItems.js:25`
    бросит, и каталог уйдёт в ветку ошибки вместо «ничего не найдено».
- **Конверт разбирается только в одном API-модуле из пяти.** Пока бэкенд не перешёл
  на коды (пункт выше), `status: false` — единственный признак провала, но проверяет его
  только `fetchItemDetails.js`. Остальные возвращают тело как есть, и в двух местах
  это даёт тот же молчаливый провал, что был на карточке вещи:
  - `CatalogPage.js:50` читает `data?.data ?? []`, поэтому ответ `{status: false}` с кодом
    200 покажет **пустой каталог без единого сообщения** — посетитель решит, что товаров нет.
  - `fetchInputData.js:9` возвращает `data.data`, то есть `undefined` на той же ошибке →
    пустые выпадающие списки на форме загрузки, тоже молча.

  `fetchWhatsappLink.js:26` деградирует мягко: ссылка не появится, но страница цела.
  `sendItemToSocial.js:19` — отдельный открытый пункт в «Мелочах» про «posted to Instagram».
  Насколько это срочно, зависит от того, при каких условиях сервер вообще отвечает
  `status: false` на списках: на детали это промах по id, а на `post/all` промаха не бывает,
  так что, возможно, только при внутренней ошибке — не проверено. Чинить точечно в каждом
  модуле смысла мало: это задача того самого низкоуровневого враппера из `TODOS.md`,
  который разберёт конверт в одном месте для всех запросов.

  Непроверенное допущение нынешней правки одно: что `status: false` на детали всегда
  означает «вещи нет». Если тем же полем сообщается отказ в доступе, пользователь увидит
  «Item not found» вместо правды. Наблюдаемое поведение за это допущение: прочие отказы
  бэкенд отдаёт кодами (`422`, `401`), конверт с `false` достался одному промаху по id.
  Форма ответа приватного эндпоинта риском больше не является: `fetchItemDetails` считает
  промахом и `status: false`, и пустое `data`, поэтому обе карточки корректны при любом
  из вариантов — `{status:false}`, настоящий 404 или успех без тела.
- **Вещь без описания не открывается на публичной карточке.** `validateItemData`
  (`Components/MainPages/CatalogItemPage/utils/Utils.js:6-14`) требует наличия всех пяти
  ключей, включая `description` (`:10`), а коммит `8d8c31b` сделал описание необязательным
  при загрузке. Если бэкенд для такой вещи ключ не присылает вовсе, карточка уходит в ветку
  «No item data»: товар виден в каталоге, но его страница не открывается. Проверка строгая
  именно по `undefined`, поэтому `null` и пустая строка её проходят — всё зависит от того,
  что именно отдаёт API для вещи без описания. Сначала сверить с бэкендом, и если ключ
  отсутствует — убрать `description` из обязательных, а не подставлять заглушку.
